# 自動車追い越し検出 (GoPro)

自転車に取り付けた GoPro 動画(前向き / 後ろ向き)から、
**自動車に追い越される瞬間**を自動検出し、区間を CSV 出力・クリップ切り出しするツール。
研究用途(追い越し時間の把握、離隔距離分析の前段)を想定。

撮影方向は `--view {front,rear}` で指定する(`detect_overtaking.py` では必須。全自動実行
`run_pipeline.py` では省略でき、その場合 [`detect_view.py`](#撮影方向の自動判定-detect_viewpy)
が自動判定する)。日本(左側通行)では追い越し車は自転車の右側を抜けていくため、
見え方が次のように異なる:

- **`--view front`(前向き)**: 追い越し車は画面の**右端付近から現れ、左(中央)へ流れて**抜ける。
- **`--view rear`(後ろ向き)**: 後方カメラは左右反転するため、追い越し車は**画面中央(消失点)付近に
  小さく現れ、左端へ大きくなりながら流れて**抜ける(前方とは奥行きの進行が逆)。

前方では路駐車両などが画面中央(消失点)付近から現れて外側の端へ流れ、後方では対向車が
逆に端付近から中央へ遠ざかる。上記の「出現位置 + 流れる向き」の条件でこれらを除外し、
追い越しの誤検知を減らせる。

**方向の取り違えは致命的**。前向き撮影を `rear` で解析した実測では、誤検知66件・
取りこぼし8件になった(同じ動画を `front` で解析すると40候補で正解12件をほぼ網羅した)。
自信が無い場合は `python detect_view.py <動画>` で先に判定するとよい(数秒で終わる)。

## セットアップ

このプロジェクトは GitHub には軽量なソースだけを置き、初回起動時に必要な実行環境を
PC上へ自動作成する。利用者が実行するファイルは `起動.bat` のみ。

```powershell
# 初回起動。portable\python、YOLOモデル、FFmpeg が無ければ自動準備する
.\起動.bat
```

初回セットアップでは次を自動で準備する。

- `portable\python` ... Python 本体と `requirements.txt` のライブラリ
- PyTorch ... CUDA対応GPUを検出した場合はGPU版、検出できない場合はCPU版を自動インストール
- `yolov8n.pt` ... YOLO の既定モデル
- `tools\ffmpeg.exe` / `tools\ffprobe.exe` ... クリップ切り出し用。既に PATH 上に ffmpeg がある場合は省略可

セットアップにはインターネット接続が必要。途中で失敗した場合、次回 `起動.bat` 実行時に
壊れた `portable\python` を検出して再作成する。

GitHub から取得した作業フォルダでは、起動時に更新確認も行う。ローカル変更が無い場合だけ
`git pull --ff-only` で自動更新し、作業中の変更がある場合は自動更新をスキップする。

### 別のPCへ持ち運ぶとき（外付けSSD運用）

このフォルダは外付けSSDに置いて複数のPCで使うことを想定している。実行環境は
`portable\python`（embeddable Python）に一本化してあり、`python313._pth` が相対パスしか
見ないので、**別のPCに挿してもドライブレターが変わっても動く**。

- **`.venv` は使わない**。venv は作成時のPython本体の絶対パスを `pyvenv.cfg` の `home =` へ
  焼き込むため、そのPythonが無いPCでは必ず壊れる。コマンドは
  `portable\python\python.exe` で実行する。
- pip も `Scripts\pip.exe` ではなく `portable\python\python.exe -m pip` を使う。
  `Scripts\*.exe` は作成時の絶対パスを埋め込んでいるので、フォルダを移すと動かない。
- 新しいPCでは最初に `起動.bat --check` を実行し、Python・CUDAが見えるか確認する。
  NVIDIA GPUが無いPCでもCPUで動く（検出は大幅に遅くなる）。
- git が `dubious ownership` を出したら、そのPCで一度だけ次を実行する。

```powershell
git config --global --add safe.directory "E:/松本研究室/programming/LiDAR解析ソフト"
```

PC依存の値（GUIの前回設定 `gui_settings.json` / `auto_gui_settings.json`、`portable\python`、解析出力）はすべて
`.gitignore` 済みなので、SSDを挿し替えても衝突しない。`起動.bat` と `全自動実行.bat` は
自分の場所（`%~dp0`）を基準に動くので、置き場所を変えても書き換え不要。

## 使い方

```powershell
# GUIを起動
.\起動.bat

# 起動環境だけ確認
.\起動.bat --check

# 更新確認を省略してGUIを起動
.\起動.bat --no-update

# コマンドラインで動画検出
.\起動.bat 入力動画.mp4 rear

# オプションを追加して検出
.\起動.bat 入力動画.mp4 front --overlay --conf 0.35
```

- ダブルクリックして GUI を起動する
- 動画ファイルを`起動.bat`へドラッグ＆ドロップする
- `起動.bat input.mp4 rear` のようにコマンドラインから実行する
- `起動.bat --check` でPython・CUDA環境だけを確認する
- `起動.bat --no-update` で更新確認を省略して起動する

## GUIワークフロー

非エンジニア向けの一連の作業画面は `起動.bat` をダブルクリックして起動する。
画面は HTML/CSS/JavaScript で作られ、Windows WebView2上にデスクトップアプリとして表示される。

1. **動画検出**: GoPro動画とカメラ方向を選び、追い越し候補とクリップを作成する
2. **クリップ確認**: 候補クリップを開き、正しい追い越しは「採用」、誤検知は「除外」にする
3. **PCAP・時刻同期**: Velodyne PCAPを読み込み、GPS自動同期でGoProとVeloViewの時刻差(オフセット)を求める
4. **点群・出力**: 候補時刻へ移動して車両点群を矩形選択し、フレーム別CSVへ出力する。
   「レビュー結果をCSV保存」で確認結果を保存する

**除外**にした候補は、手順3の時刻一覧と手順4の候補選択の対象から自動的に除かれる。

LiDAR画面はclassic PCAP内の標準1206-byte Velodyneデータパケットを直接読み込む。
VLP-16、HDL-32E、VLP-32Cに対応し、点群は上面図で表示される。ドラッグで対象車両を囲い、
開始・終了フレームを指定して出力すると、各フレームの選択点が個別CSVになる。
CSVの9・10列目は従来工程と同じ `Points:0`（X）・`Points:1`（Y）。

GUIの入力内容とショートカット設定は `gui_settings.json` に保存される。確認済みイベントは
`out/reviewed_overtaking_events.csv` に保存され、次回起動時にも引き継がれる。
確認用クリップはGUI内の動画プレイヤーで再生できる。

候補確認画面のショートカット（既定値）:

- `A`: 採用
- `D`: 除外
- `W`: 未確認へ戻す
- `B` / `N` / `M`: 選択中候補の車種を 軽 / 普通 / 大型 に変更
- `Space`: 再生 / 一時停止
- `←` / `→`: 前後の候補へ移動

採用・除外のキーと車種キーは候補確認画面の「⌨ キー設定」から変更でき、`gui_settings.json` に
保存される。採用または除外を決定すると、次の候補へ自動的に移動して再生する。候補一覧の開始・
終了時刻は `◯分◯秒` 表記で表示される。車種は **大型・普通・軽** の3分類で表示され、
候補一覧の選択欄から手動修正できる。
旧形式のCSVには黄色ナンバー情報が保存されていないため、軽判定を反映するには動画検出を
再実行する必要がある。旧結果を読み込んだ場合はGUIに再解析の警告が表示される。
再解析時は新しい自動判定を採用し、候補一覧でユーザーが手動変更した車種だけを引き継ぐ。

GUIを開かず起動環境だけ確認する場合:

```powershell
.\起動.bat --check
```

撮影セッションフォルダを指定すると、検出から最終Excel出力までを1コマンドで通す。
GUIのStep1〜6を人が順に操作する代わりに使う。

```powershell
portable\python\python.exe run_pipeline.py E:\データ\260701\ID1 --skip-detect   # 検出済みの続きから
```

### 実行ファイル (全自動実行.bat)

コマンドを打たずに同じ処理を起動する実行ファイル。`起動.bat` (GUI用) と対になる。

- **ドラッグ＆ドロップ**: セッションフォルダを `全自動実行.bat` へ落とす
- **ダブルクリック**: セッションフォルダのパスを聞いてくる (ウィンドウへフォルダを
  ドロップして貼り付けてもよい)
- **コマンドライン**:

```powershell
.\全自動実行.bat E:\データ\260701\ID1
.\全自動実行.bat E:\データ\260701\ID1 --view rear --organize-id 1
.\全自動実行.bat E:\データ\260701\ID1 --no-setup   # 環境の確認・準備を省略する
```

フォルダ以外の引数はそのまま `run_pipeline.py` へ渡す。`起動.bat` と同じく初回は
`portable\python`・`yolov8n.pt`・`tools\ffmpeg.exe` を自動準備し (`--no-setup` で省略)、
`portable\python` が使えない場合は `.venv\Scripts\python.exe` を使う。GitHubの更新確認は
行わない。完了後に `report.html` を開くか聞いてくる。

### 専用GUI (全自動実行GUI.bat / auto_gui.py)

全自動実行を画面から操作する専用GUI。従来のワークフローGUI（`起動.bat` / `web_gui.py`）
とは**独立したアプリ**で、`全自動実行GUI.bat` のダブルクリックで起動する
（画面は `web_ui_auto/`、前回の入力は `auto_gui_settings.json` に保存）。

画面は2つ。

1. **実行**: セッションフォルダを選び、必要なら撮影方向（既定は自動判定）・検出の扱い
   （通常／スキップ／やり直す）・整理ID・被験者・収集日・**道路の車線数**・時刻オフセット・
   追加オプション（`--skip-sync-check` など空白区切り）を指定して開始する。車線数は
   `--lane-count` として渡り、全候補の「車線数」列の既定値になる（確認画面で候補ごとに
   直せる）。段階の完了ごとに進捗バーと段階一覧が更新され（`PipelineReport.stage` が出す
   `[stage]` 行を解析。検出中はYOLOのフレーム進捗も反映）、「中止」で検出の孫プロセスごと
   止められる（taskkill /T）。実行済みの出力フォルダを開いて確認画面だけ使うこともできる
2. **確認・修正**: 完了すると自動で切り替わる。追い越しデータ（reviewed CSV の候補）を
   1件ずつクリップで確認し、採否（採用/除外/未確認。`A`/`D`/`W`、`←`/`→` で移動）と
   車種を手動修正できる。加えて**危険感**（1〜3）と**道路の車線数**を候補ごとに入力する。
   プレビューの「点群ビュー」タブでは、その候補の切り抜き点群を上面図（X-Y）と側面図
   （Y-Z）で表示する（report.html のビューアと同じ表示。フレームスライダーと再生、
   Intensity/高さZ の色切り替え、自転車=原点・通過区間 |Y|<3m・離隔距離LC・フェーズ点の
   補助線。データは `out/lidar/overtaking_*.csv` から読むため `--no-report` でも使える。
   `Space` は表示中のタブの再生/停止に効く）。
   「修正をCSVへ保存」で `reviewed_overtaking_events.csv` へ書き戻し、
   「最終Excelを再生成」で保存と最終Excel（末尾に「車線数」列。整理ID等は
   実行レポートから引き継ぐ）までを通す。自動レビューの理由・警告・人手項目も画面に出る。
   既定では「未確認」の条件はすべて除外されるため確認対象は採用行のみ。未確認を残して
   GUIで採否を決めたい場合は、実行画面の追加オプションに `--keep-unconfirmed` を付ける

### 車長込みの相対速度への変換 (車長変換GUI.bat / AutoAnalysis/)

既存の解析結果を、本体の 2026-11-07 以降の式（`docs/計算方法.md` 9.2・9.5・9.6）へ直す道具一式。
コードは `AutoAnalysis/` にまとまっていて、元の解析結果は一切書き換えない。

| 指標 | 旧 | 新 |
|---|---|---|
| 通過時間 | `t(フェーズ4) − t(フェーズ3)` | `t(フェーズ4の1つ前の行) − t(フェーズ3)` |
| 相対速度 | `距離p3 ÷ 通過時間 × 3.6` | `3.6 × (距離p3 + 車長) ÷ 通過時間` |
| TTC | `距離p2 ÷ (相対速度 ÷ 3.6)` | `フェーズ2の distance ÷ (フェーズ2の speed ÷ 3.6)` |
| 自動車速度 | `自転車速度 + 相対速度` | 同じ式（新しい相対速度で計算し直す） |

単独でも配布するため本体のコードは読まず、解析xlsx の行（点の列とフェーズ区分）から計算し直す。
既存の解析結果 401 件で、本体の `analyze_edit_points` と通過時間・TTC が全件一致することを確かめてある
（`test_car_length.py` でも照合している）。車長の無いイベントも通過時間と TTC は新しい式へ直し、
相対速度・自動車速度だけ空欄にする。

> 2026-11-07 から本体の全自動実行が段階6.5（[車長推定](#車長推定段階65--car_lengthpy)）で同じ式の値を
> 直接出すようになった。このツールはそれより前に作った解析結果を変換するためのもの。ここで推定・確認した
> 車長は `car_length.py --import-lengths` で本体の各セッションへ取り込める。

1. `extract_car_images.py` … `clips/` の動画から追い越し車の写真を切り出す（YOLO + ByteTrack。
   `car_images/` が ChatGPT へ送る切り抜き、`car_frames/` が枠を描いた確認用）
2. `car_length_gpt.py` … 写真を ChatGPT（OpenAI API）へ送り、車名とカタログ全長を推定して
   `car_lengths.csv` へ書く。生の応答は `gpt_raw/` に残す。APIキーは `AutoAnalysis/.env` の
   `OPENAI_API_KEY`（.gitignore 済み。絶対にコミットしない）。`source=manual` の行は上書きしない
3. `convert_relative_speed.py` … `car_lengths.csv` を使って解析xlsx と最終Excel を変換する
   （`xlsx_cells.py` でセルだけ差し替えるので書式や危険感などの手入力列は保たれる）。
   車長の無いイベントは相対速度を空欄にし、`--fallback lidar`（点群の実測長）/ `--fallback class`
   （車種の代表値）で代用できる。全イベントの新旧比較（通過時間・相対速度・TTC・自動車速度）は
   `converted/conversion_summary.csv`。解析xlsx には旧値と3つの式も書き足す

**フォルダ**: 入力は「解析結果フォルダ」（セッションごとの `lidar_edit/` `final/` `clips/` を
含むフォルダ。例: `output/`）。写真・`car_lengths.csv`・`gpt_raw/`・`converted/` はすべて
「保存先フォルダ」に入り、既定では解析結果フォルダの隣に `<フォルダ名>_車長変換`
（例: `output_車長変換/`）を作る。`*_車長変換/` は .gitignore 済み。

`AutoAnalysis/length_pipeline.py` が3段階を順に実行する（`--src` で解析結果フォルダ、`--work` で
保存先を指定。どの段階も未処理分だけ扱うので何度実行してもよい。セッションの限定・作り直し・
代用などの細かい指定はこのコマンドのオプションで行う。リポジトリ直下の `run_pipeline.py` は
全自動解析の方で別物）。`車長変換GUI.bat` のダブルクリックで専用GUI（`AutoAnalysis/length_gui.py`、
画面は `AutoAnalysis/web_ui_length/`、前回のフォルダ指定は `length_gui_settings.json`）が起動する。

1. **実行**: 解析結果フォルダ（必要なら保存先も）を選び、「実行」ボタン1つで3段階を既定の設定
   （採用イベントのみ・既存は飛ばす・車長の無い行は空欄）で通す。進捗バー・段階一覧・ログが
   更新され、「中止」で YOLO/GPT の子プロセスごと止められる。ChatGPT の API キーは同じ画面で
   貼り付けて保存する（`AutoAnalysis/.env` に書かれ、そのPCだけで使う。値は画面に出ない）。
   下の表にセッションごとの写真・車長・変換済み/未取得の数が出る
2. **車長の確認・修正**: 切り抜き写真/全体フレームと GPT の車名・確度・判断理由を見て車長を
   確かめる（`←`/`→` で移動、一覧は「写真あり / 要確認 / 手入力 / すべて」で絞れる）。
   数値を直して保存すると「手入力」（`source=manual`）になり、以後の再推定でも上書きされない。
   「手入力を取り消す」で `gpt_raw/` の生応答から GPT の値へ戻す。直した後に実行画面で
   もう一度「実行」を押すと Excel に反映される（段階1・2は済んでいる分を飛ばす）

**別のPCへ配布するとき**: `portable\python\python.exe AutoAnalysis\make_dist.py` で
`dist\車長変換ツール\`（と同名の zip）ができる。これは git に依存しない単独フォルダで、コード一式・
初回セットアップ用の `requirements.txt` と `prepare_portable_python.ps1`・起動 bat・`はじめに.txt` を含み、
`.env` や解析データは含まない。渡した先では `車長変換GUI.bat` をダブルクリックするだけでよい。
作業フォルダごと（git clone か外付けSSD）持っていく場合も同様に、
`車長変換GUI.bat` をダブルクリックする。初回は他のランチャーと同じく `portable\python` と
`yolov8n.pt` を自動準備する（インターネット接続が必要）。起動したら解析結果フォルダを選び、
API キーを貼り付けて保存すれば使える。PC依存のもの（`.env`・`length_gui_settings.json`・
`*_車長変換/`）は .gitignore 済みなので、持ち運んでも衝突しない。
`length_gui.py --check` で画面なしの検証、`--serve-only` でブラウザから同じ画面を使える。

### 入力フォルダの規約

```text
<セッション>\           … フォルダ名が既定の被験者ID (例 ID1)
  GOPRO\*.MP4          … GoPro動画。ファイル名順に1本の連結タイムラインとして扱う
  LiDAR\*.pcap         … Velodyne PCAP (1つ)
  metadata.json        … 任意。{"subject":..,"date":..,"view":..,"organize_id":..}
```

親フォルダ名が `YYMMDD`(例 `260701`)ならデータ収集日として使う。`metadata.json` があれば
読み込み、CLI引数のほうが優先される。動画やPCAPが規約どおりに置かれていない場合は
`--videos` / `--pcap` で明示指定する。

### 主なオプション

| オプション | 既定 | 説明 |
|-----------|------|------|
| `--out` | `<セッション>\out_auto` | 出力先 |
| `--view` | (自動判定) | 撮影方向。`front` / `rear`。省略時は `metadata.json` → 自動判定の順 |
| `--view-samples` | `3` | 自動判定でサンプルする時間帯の数 |
| `--view-sample-seconds` | `60` | 自動判定サンプル1箇所の長さ(秒) |
| `--subject` | セッションフォルダ名 | 被験者名またはID |
| `--date` | セッションの親フォルダ名 | データ収集日 (`YYMMDD` / `YYYY-MM-DD`) |
| `--organize-id` | (空) | 整理ID。空なら候補IDを使う |
| `--lane-count` | (空) | 道路の車線数。全候補の「車線数」列（reviewed CSVと最終Excel）の既定値。`metadata.json` の `lane_count` でも指定できる |
| `--videos` / `--pcap` | (自動発見) | 入力を明示指定する |
| `--skip-detect` | off | 段階1のYOLO検出を行わない (既存CSVを使う) |
| `--redetect` | off | 既存CSVがあっても検出をやり直す |
| `--skip-gps` | off | 段階2のGPSテレメトリ抽出を行わない |
| `--offset` | (GPS自動同期) | 時刻オフセット(秒)を手動指定する。指定すると段階3.5の検証は行わない |
| `--skip-sync-check` | off | 段階3.5の時刻同期の自己検証を行わない (1セッション約3分かかる) |
| `--no-auto-offset` | off | 自己検証の推定オフセットが3秒超ずれていても差し替えない（既定は差し替える） |
| `--track-margin` | (撮影方向別) | 点群追跡のマージン(秒)を前後同じ値で明示する。既定は `front` が開始側-8秒/終了側+3秒、`rear` がその逆 |
| `--max-lane-clearance` | `3.5` | 自動レビューで隣車線の通過として除外する離隔距離(m) |
| `--review-lane-clearance` | `2.6` | これを超える離隔距離の候補を「未確認」にする(m)。隣車線の車を掴んだ疑い |
| `--no-ego-gate` | off | 自車運動（停止・低速・旋回）による足切りを行わない |
| `--stop-speed` | `1.0` | これ未満の自車速度は停止中とみなして除外する(m/s) |
| `--turn-yaw-rate` | `20` | これを超える旋回中の候補を「未確認」にする(度/秒) |
| `--keep-unconfirmed` | off | 自動レビューの「未確認」を従来どおりレビューCSVへ残す。既定は未確認の条件をすべて「除外」にする |
| `--no-lidar-extra` | off | 動画側に候補の無い車を `L###` の「未確認」行として起票しない |
| `--no-report` | off | 段階7bの閲覧用HTMLレポート (`out\report.html`) を作らない |
| `--no-car-length` | off | 段階6.5の車長推定（写真を ChatGPT へ送る）を行わない。車長が無い候補の相対速度・自動車速度は空欄 |

`overtaking_events.csv` が既にある場合、段階1は自動でスキップされる。

### 実行される段階

0. **撮影方向** — `--view` も `metadata.json` の `view` も無ければ
   [`detect_view.py`](#撮影方向の自動判定-detect_viewpy) で自動判定する。
   判定不能なら `front` を仮定し、警告と人手項目を残して続行する
1. **検出** — `detect_overtaking.py` をサブプロセス実行 (`--view` / `--out` / `--clip`)
2. **GPS抽出** — 各動画のGoProテレメトリ → `out/gps/<動画名>/telemetry_gps.xlsx`。失敗しても続行
3. **時刻同期** — 先頭動画のGPS UTCとPCAP開始時刻からオフセットを算出 → `out/sync.json`
3.5. **同期の自己検証** — `tools/sync_check.py` でGPS速度とLiDAR自車速度の相互相関から
   オフセットを独立に推定し、段階3の値と突き合わせる → `out/sync_check.json`
   （自車速度の時系列は `out/sync_series.npz`）
4. **点群自動追跡** — 候補と車両を1対1に割り当てて追跡 → `out/lidar/overtaking_*.csv`
5. **edit CSV** — 最近接点の軌跡と解析Excel → `out/lidar_edit/`
6. **自動レビュー** — LiDARの結果と自車運動で採否を判定 → `out/reviewed_overtaking_events.csv`
6.5. **車長推定** — 動画から追い越し車の写真を1枚切り出し、ChatGPT で車長を求める → `out/car_length/`
   （[下記](#車長推定段階65--car_lengthpy)）。推定後に解析Excelを作り直す
7. **最終Excel** — `out/final/<出力フォルダ名>_final.xlsx`
7b. **閲覧用レポート** — 動画クリップと点群を見る `out/report.html`（[下記](#結果閲覧用htmlレポート-make_reportpy)）
8. **レポート** — `out/pipeline_report.json` と `out/pipeline_report.txt`

自動レビューは点群の結果を使うため追跡より後に置く。動画だけでは隣車線の車や誤検知を
切り分けられないが、離隔距離まで求まれば機械的に落とせる。さらに段階2のGPS（無ければ
段階3.5の自車速度）から、自転車が停止中・旋回中だった候補も落とす。

レポートには各段階の成否、オフセット値、候補数、警告、**人手が必要な項目**の一覧が出る。
段階2〜7は個別の失敗で止まらず、その候補を「手動作業が必要」としてレポートへ記録して続行する。

### 車長推定（段階6.5 / car_length.py）

相対速度は `3.6 × (距離p3 + 車長) ÷ 通過時間` で求める（`docs/計算方法.md` 9.5）。車長は
「除外」以外の候補ごとに次の手順で求める。

1. 動画（`out/clips` のクリップ、無ければ元動画）の最接近時刻の前後を YOLO + ByteTrack で調べ、
   追い越し車が画面の端で切れずに最も大きく写った1枚を切り抜く → `out/car_length/images/<ID>.jpg`
   （確認用に枠を描いた全体は `frames/`）
2. その1枚を ChatGPT（OpenAI API、既定 `gpt-5.5`）へ送り、車名とカタログ全長（特定できなければ
   形状からの推定）を答えさせる。生の応答は `gpt_raw/` に残す
3. `out/car_length/car_lengths.csv` に書く（`source` が `manual` の行は上書きしない。推定済みの行は
   次回の実行でも推定し直さない）

APIキーは環境変数 `OPENAI_API_KEY`、無ければリポジトリ直下の `.env`、`AutoAnalysis/.env` の順に
探す（`.env` は .gitignore 済み。絶対にコミットしない）。キーが無い・写真を切り出せない・車長を
特定できなかった候補は、相対速度と自動車速度が空欄になり、最終Excelの警告と人手項目に残る。
`car_lengths.csv` の `car_length_m` に手入力（`source` は `manual`）して最終Excelを再生成すれば反映
される。最終Excelの末尾には使った車長と出典（`車長(m)` `車長の出典`）の列が付く。

既存の出力フォルダには後から実行できる（推定後に解析Excelと最終Excelを作り直す）。

```powershell
.\portable\python\python.exe car_length.py --out output\w5o\ID1            # 推定
.\portable\python\python.exe car_length.py --out output\w5o\ID1 --dry-run  # 写真の切り出しだけ（APIは呼ばない）
.\portable\python\python.exe car_length.py --import-lengths output_車長変換\car_lengths.csv --src output
    # 車長変換ツールで推定・確認済みの車長を各セッションへ取り込む（APIは呼ばない）
```

### 時刻同期の自己検証（段階3.5）

段階3のオフセットは GoPro の GPMF 時刻と PCAP の記録時刻の引き算なので、LiDAR 収録PCの
時計がずれていると丸ごとずれる（260701 のデータでは全5セッションで +4.2〜5.2 秒ずれていた）。
段階3.5 では点群から自車速度を作り直し、GPS 速度との相互相関でオフセットを独立に推定して
突き合わせる。差の扱いは3段階。

| 差 | 扱い |
|---|---|
| 1.0秒以内 | 記録のみ（同期の精度内） |
| 3.0秒以内 | 警告（車両の割り当てがずれる可能性） |
| 3.0秒超 | **推定値へ差し替えて先へ進む**（`--no-auto-offset` を付けた場合だけ差し替えず、人手項目にする） |

相関ピーク < 0.50、突出度 < 0.15、区間ごとのばらつき > 2.0秒 のいずれかなら「推定値を
信用できない」として何もしない。差し替えたときは `sync.json` が `source="sync_check"` に
なり、段階3の値は `gpmf_offset` に残る。GPMF 側からはPCの時計ずれを見られないので、
**独立に測った推定値のほうを既定で採る**（以前は `--auto-offset` を付けたときだけだったが、
付け忘れると全セッションが数秒ずれたまま処理されるため既定にした。`--auto-offset` は
そのまま指定できる）。検証自体は `--skip-sync-check` で省ける。

### イベント↔車両の割り当て

追い越しが連続する車列では、1つの追跡窓に複数の車が入る。スコア最大の車を選ぶと
「同じ車が複数の候補へ出力される」「隣のイベントの車を掴む」が起きるため、次の順で
1対1に割り当てる。

1. 候補ごとに追跡窓を走査し、追い越し車らしいトラックを**全部**集める
   (`track_overtaking` の `candidates`)
2. 動画側の基準時刻 + 時刻オフセットを**期待通過時刻**とする。基準は最接近時刻
   `peak_t_s`(bbox面積が最大のフレーム)だが、検出トラックが途中で別の車へ乗り移ると
   peak が開始のはるか後ろへ流れるため、追い越し車が横に並ぶ瞬間 —— front 撮影なら
   画角へ入る `t_start_s`、rear 撮影なら消える `t_end_s` —— から3秒より離れた peak は
   端の時刻へ丸める(`pass_anchor`)。実際の通過時刻との系統ずれ(GPS同期誤差・
   カメラの見え方)は全候補の中央値から測って補正する (260701/ID1 では約 +1.7 秒)
3. **同一車線の車を優先**した上で、期待通過時刻との差が小さいペアから確定していく
   グリーディ割り当て。追跡窓には隣車線の車も入るので、時刻だけで選ぶと期待時刻が
   僅かにずれただけで隣車線の車(離隔距離3m前後)を掴み、そのイベント本来の車が
   どこにも割り当たらないまま捨てられる。離隔距離の目安が 2.6m 以下の候補を先に
   確定させ、同一車線の候補が無いイベントには隣車線の車も割り当てる
4. 同じ車を取り合ったら期待時刻に近い候補が勝ち、負けた候補は次点(車列の2台目)を
   選び直す (`exclude_track_keys`)。「同じ車」は**通過時刻が1秒以内かつ横位置が
   1.5m以内**で判定する。時刻だけで束ねると、隣の車線を車が流れている最中の
   追い越しで同一車線の車と隣車線の車が1台にまとめられ、束ねたグループは1つの
   イベントにしか割り当てられないので、同一車線の車がどこにも出てこなくなる
   (260701/ID1 の 608.6s。正解 LC 1.02m の車を追跡できていたのに、0.1〜0.8秒違いで
   通る隣車線の3台と1台扱いされ、採用されたのは隣車線の車だった)
5. 出力直前に、`track_key` と矩形の軌跡の重なりの両方で同一車両の重複を止める

段階4は候補一覧・期待通過時刻・割り当て結果を `out/lidar/autotrack_candidates.json`
へ落とす。割り当ての規則を変えて試すとき、点群の走査(1セッション数分)をやり直さずに
済むための診断用ファイルで、パイプラインの動作には使わない。

どの候補にも割り当たらなかった追い越し車は、**動画検出の取りこぼしの可能性**として
レポートの人手項目に挙げ、あわせて `L001` … の候補IDで起票する。その車が見つかった
追跡窓を通過時刻つきで走査し直し、`out/lidar/overtaking_L001.csv` → edit CSV →
レビューCSVの `review_status="未確認"` の行、まで通す。最終Excelは採用行だけなので、
人がクリップと点群を確認して採用に変えるまでは出力に混ざらない。既定では自動レビューが
未確認をすべて除外へ落とすため、`L###` 行をレビューCSVへ残すには `--keep-unconfirmed`
が必要（点群CSV・edit CSVとレポートの人手項目は既定でも残る）。起票が邪魔なときは
`--no-lidar-extra` を付ける(前回実行の `L###` 出力も消える)。

### 自動レビューの判定

上から順に見て、最初に当てはまった判定になる。表の「未確認」は条件の分類で、
**既定ではこれらもすべて「除外」（不採用）へ落とし、人手確認を挟まない**。
どの条件で落ちたかは `review_reason` とレポートの `reasons` に残る。従来どおり
「未確認」としてレビューCSVへ残し、人がGUIで採否を決めたい場合は
`--keep-unconfirmed` を付ける。

| 条件 | 判定 |
|------|------|
| LiDAR発の行 (`L###`。動画側に候補が無い車) | 未確認 (人が採否を決める) |
| LiDARで対応する車両が見つからない | 除外 |
| 自転車が停止中 (自車速度 < `--stop-speed`、既定1.0m/s) | 除外 |
| 離隔距離 LC > `--max-lane-clearance` (既定3.5m) | 除外 (隣車線の通過) |
| 離隔距離 LC > `--review-lane-clearance` (既定2.6m) | 未確認 (隣車線の車を掴んだ疑い) |
| フェーズ3→4で車が前進していない (距離p3 ≤ 0) | 未確認 (通過区間を抜けるまで追えていない) |
| 距離p3 < 4.5m | 未確認 (通過区間を抜けきれていない) |
| フェーズ2・4や通過時間の終端を代用している | 未確認 (距離p2・通過時間・TTCが実測でない) |
| 自転車が低速 (自車速度 < 2.0m/s) | 未確認 (発進直後・停止直前) |
| 自転車が旋回中 (> `--turn-yaw-rate`、既定20度/秒) | 未確認 (曲がり角) |
| 追跡の確信度 < 0.5 | 未確認 (レポートの人手項目へ) |
| それ以外 | 採用 |

離隔距離は edit 解析の実測値を優先し、求まらない場合だけ追跡時の目安値を使う。
`reviewed_overtaking_events.csv` には除外以外(採用・未確認)を出力し、最終Excelには
採用だけが並ぶ。既定では未確認が発生しない（すべて除外へ落ちる）ため、レビューCSVは
採用のみになる。`--keep-unconfirmed` を付けたときだけ未確認の行が残る。

#### 自車運動（停止・低速・旋回）の判定

停止中と旋回中は追い越しの前提が崩れている。停止中は静止物が後退しないので
`lidar_autotrack.estimate_forward_sign` が前進方向を +Y と決め打ちし、通過時間・
相対速度・TTC がどれも成り立たない。旋回中はセンサのヨーで静止物が横へ流れ、
追い越し車と見分けがつかない(自車運動補正は行っていない)。

判定には段階2のGPS(`out\gps\<stem>\telemetry_gps.xlsx` の間引き無しシート、約10Hz)を
使い、GPSが無ければ段階3.5が残す自車速度の時系列(`out\sync_series.npz`、中身はCSV)で
代用する。速度はイベント区間(前後1.5秒)の中央値、旋回は3m進むごとに測った進行方位の
変化率の最大値。どちらの時系列も無ければこの3つの判定は自動で省かれる
(`--no-ego-gate` で明示的に切ることもできる)。

#### 実データでの効き (260701/ID1)

人手のまとめExcel(正解12件)と突き合わせた結果。

| | 変更前 | 変更後 |
|---|---|---|
| 採用 | 20件 (正解と一致 11 / 誤り 9) | 11件 (正解と一致 11 / 誤り 0) |
| 未確認 | 4件 | 12件 |

落ちた9件の内訳は、隣車線の車を掴んだもの7件(実測LC 3.10〜3.48m)、信号待ちの停止中に
横を通った車1件(自車速度 0.33m/s)、通過区間を抜けきる前に追跡が切れたもの1件
(距離p3 2.51m)。正しく追えた11件の実測LCは 0.93〜1.89m で、誤りとの間は空いている。

正解12件のうち1件(608.6s)は、同一車線の車ではなく隣車線の車を掴んでいたため未確認へ
回る。採用行に混ぜると離隔距離が 1.02m → 3.1m と誤るので、人が点群を見て直す。

> この計測は未確認を残す従来動作（現在の `--keep-unconfirmed` 相当）でのもの。
> 現在の既定では未確認の12件も除外になり、採用の11件だけが残る。

### 車種の決め直し

自動レビューの直前に、車を割り当てられた行の車種を**点群で測った車体寸法**で決め直す
(`run_pipeline.lidar_vehicle_class`)。動画側の判定(YOLOのクラス投票と黄色ナンバー検出)は
ミニバンを`truck`と呼ぶ・トラック後部の黄色い標示を軽のナンバーと見る、の2方向へ外れる。

| 条件 | 車種 |
|------|------|
| 車体長 × 車高 >= 9.0 m² (側面のシルエット面積) | 大型 |
| 2.50m <= 車体長 <= 3.50m かつ 1.20m <= 車幅 <= 1.80m | 軽 (軽自動車規格 3.40×1.48m) |
| それ以外 | 普通 |

寸法が測れていない行(追跡失敗・旧プラグイン)、人がレビューで直した行
(`class_reviewed`)、LiDAR発の`L###`行(車種は空欄)は書き換えない。
しきい値の根拠と過学習の確認は `docs/計算方法.md` の 3.1 にある。

### 点群自動追跡プラグイン

段階4は `lidar_autotrack` モジュールを任意の依存として読み込む。モジュールが無い場合は
その候補を「GUIで手動選択が必要」としてレポートに記録し、残りの段階を続行する。

```python
from lidar_pcap import VelodynePcap

def track_overtaking(pcap: VelodynePcap, first_frame: int, last_frame: int,
                     side: str = "right",
                     expected_pass_time: float | None = None,
                     exclude_track_keys: list[str] | None = None) -> dict:
    """追い越し区間のフレームごとに車両を囲う矩形を返す。

    expected_pass_time: 期待通過時刻(pcap相対秒)。指定するとスコア最大ではなく
        「|Y|<3m を横断する時刻がこれに最も近いトラック」を選ぶ
    exclude_track_keys: 他イベントへ割り当て済みのトラックを除いて次点を選ぶ

    戻り値: {
        "ok": bool,
        "frames": [{"index": int,
                    "bounds": {"min_x":.., "max_x":.., "min_y":.., "max_y":..}}],
        "confidence": float,
        "warnings": [str],
        "pass_time": float | None,   # 選んだトラックが |Y|<3m を横断した時刻
        "track_key": str | None,     # 同一車両を指す識別子
        "candidates": [{"track_key", "pass_time", "score", "median_x", "lc_estimate",
                        "length", "width", "height", "near_length", "points"}],
    }
    """
```

`candidates` の `length` / `width` / `height` は点群で測った車体寸法(m)で、
呼び出し側の車種判定に使う(下記「車種の決め直し」)。

後ろ3つのキーと引数2つは任意。受け取らない古いプラグインでも動くよう、呼び出し側は
署名を見て渡すかどうかを決める。通過側は日本では常に右(+X)なので、候補CSVの `side` 列
(カメラの見え方 front=left / rear=right)ではなく常に `"right"` を渡す。

### 撮影方向の自動判定 (detect_view.py)

`--view` を人が指定しなくても済むように、GoPro動画から撮影方向を自動で決める。
`run_pipeline.py` では **`--view` も `metadata.json` の `view` も無い場合だけ** 走る
(明示指定が常に優先)。単体でも使える:

```powershell
portable\python\python.exe detect_view.py E:\データ\260701\ID1\GOPRO\GX010731.MP4
portable\python\python.exe detect_view.py <動画...> --json          # 結果をJSONで出す
portable\python\python.exe detect_view.py <動画...> --with-detection # 検出件数も参考表示
```

**原理: 背景オプティカルフローの放射方向**。自転車が前進しているとき、

- **前向きカメラ** … 世界は消失点から**外向きに湧き出す**ように流れる(拡大)
- **後ろ向きカメラ** … 世界は画面中央へ**吸い込まれる**ように流れる(縮小)

これは撮影方向そのものが決める幾何なので、交通量・道路種別・時間帯に依存しない。
動画の全長の20% / 50% / 80%付近から60秒ずつ取り、特徴点をLK法で追跡して
「画面中心から外向きの成分 ÷ 変位量」の中央値を測る。**+なら front、−なら rear**。

自転車が**停止している間は背景が動かず**符号が定まらない(実測 0.03〜0.18px)ため、
背景変位が 2.0px 以上のフレーム対だけを使い、走行中のフレーム対が30組に満たなければ
別の時間帯を追加サンプルする。決着が付いた時点で打ち切るので、走り出しの動画なら
1サンプル・**数秒**で終わる。確信度が 0.65 に届かなければ「判定不能」を返す。

実測(いずれも正しく判定。所要時間はGPU不要):

| 動画 | 正解 | 放射成分 | 判定 | 確信度 | 所要 |
|------|------|---------|------|-------|------|
| 260701/ID1 `GX010731.MP4` | front | +0.87 | front | 0.99 | 1.3秒 |
| 260701/ID2〜ID5 (各先頭) | front | +0.61〜+0.97 | front | 0.99 | 1〜3秒 |
| 1.海野/gopro_前 `GX010729` | front | +0.74 | front | 0.99 | 31秒 |
| 1.海野/gopro_前 `GX020729` | front | +0.87 | front | 0.99 | 1.5秒 |
| 1.海野/gopro_後 `GX010714` | rear | -0.47 | rear | 0.95 | 15秒 |
| 1.海野/gopro_後 `GX020714` | rear | -0.45 | rear | 0.91 | 1.4秒 |

所要時間が伸びている動画は、停止中の時間帯が多く追加サンプルまで進んだもの。

> **検出件数の比較は主判定に使わない**。「front / rear 両方で `detect_overtaking.py` を
> 回し、イベントが多い方を採用する」案は実データで**逆の答えを出した**。260701/ID1
> (前向き)の60秒クリップで front 1件 / rear 15件、動画全体でも rear 66件 / front 40件
> になる。後方設定の軌跡条件(中央から左端へ流れる)は前向き映像の路駐車両・対向車にも
> 当てはまるため、**誤った方向のほうがイベントが増えうる**。件数は `--with-detection` で
> 参考値として記録できるが、判定には使わない。

判定不能だった場合、パイプラインは `front` を仮定したうえで警告と
「撮影方向を確認して `--view` で再実行」という人手項目をレポートへ残す。

### 結果閲覧用HTMLレポート (make_report.py)

段階7bは、解析結果を人が見て確かめるための1枚のHTML `out\report.html` を作る。イベント一覧を
クリックで開くと、そのイベントの**動画クリップ**（`clips\event_NNN_side.mp4` を相対パスで参照。
コピーしないので容量は増えない）と、**切り抜いた点群のビューア**（上面図 X-Y と側面図 Y-Z の2面。
フレームスライダーと再生/停止でフレーム送り、色は Intensity と高さZ を切り替え、自転車=原点・
通過区間 |Y|<3m の帯・離隔距離LCの位置・フェーズ1〜4の点を補助線で表示）が並ぶ。
ヘッダにはセッション名・実行日時・採用/未確認の件数、カードには離隔距離LC・通過時間・相対速度・
TTC・車種・レビュー理由が出る。既存の出力フォルダからは
`portable\python\python.exe make_report.py --out output\ID1` でいつでも作り直せる
（`--max-points-per-frame` / `--max-points-total` で点群の間引き量を変えられる）。
**ダブルクリックで開ける file:// 前提**なので外部CDNもネット接続も使わず、点群だけは
`report_data\event_NNN.js`（`window.__EVT["001"]=...` の代入文）に分けてカードを開いたときに
`<script>` 要素で遅延読み込みする（file:// では `fetch` が使えないため）。点群は座標を小数2桁に
丸め、1フレーム2000点・1イベント6万点を上限に等間隔で間引くので、1イベントあたり
0.2〜0.8MB 程度（実データID1の24件で `report_data` 合計11MB、`report.html` 47KB、生成7秒）。
`--skip-detect` などで `clips\` が残っていない場合は動画欄が「クリップなし」になり、点群だけの
レポートとして成立する。

### 危険感の扱い

危険感は被験者の申告値なので全自動実行では**空欄**にする。最終Excelの「危険感」列は
レビューで 1〜3 を明示した場合だけ「やや危険 / 危険 / 非常に危険」になり、未設定なら空欄。
セルには従来どおり入力候補のリストが付いているので、後から人が選択して埋める。
専用GUI（`全自動実行GUI.bat`）の確認画面で候補ごとに入力してから再生成してもよい。

最終Excelの末尾には**「車線数」列**（S列）がある。道路の車線数は自動では求まらないため、
`--lane-count`（専用GUIの実行画面の「道路の車線数」）で全候補の既定値を先に入れるか、
専用GUIの確認画面で候補ごとに入力して「最終Excelを再生成」すると埋まる
（reviewed CSV の `lane_count` 列から転記。既存列の位置・入力規則は変えていない）。

## 速度・高速化

検出を**バッチ推論**し、追跡(ByteTrack)だけ逐次更新する構成。1フレームずつ
処理するより GPU 使用率が上がり、実測で数倍高速(640px・RTX2070で約8倍)。

優先度の高い高速化:

1. **GPU版 torch**(最重要)。CPU版だと桁違いに遅い。初回セットアップでは CUDA対応GPUを検出した場合にGPU版、検出できない場合にCPU版を自動インストールする。導入確認:
   ```powershell
   .\起動.bat --check
   ```
   CUDA対応GPUがあるのに `CUDA: False` になる場合は、NVIDIAドライバを確認する。PyTorch の取得先を手動指定したい場合だけ、初回セットアップ前に次の環境変数を指定してから `起動.bat` を実行する:
   ```powershell
   $env:TORCH_INDEX_URL = "https://download.pytorch.org/whl/cu128"
   .\起動.bat
   ```
2. **`--imgsz 416`(または 320)** で推論解像度を下げる(精度とのトレードオフ)。
3. **`--batch`** を VRAM が許す範囲で大きく(既定32)。OOM 時は下げる。
4. **`--overlay` を付けない**(可視化動画の書き出しは I/O コストが高い)。
5. 既定で動画をRAMへ2バッチ先読みし、読込とGPU推論を並列実行する。メモリを
   節約したい場合は `--prefetch-batches 0`、余裕があれば2～4を目安にする。
6. 背景フローは既定で3フレームごとに計算する。`--flow-stride 1`で従来どおり
   毎フレーム計算できるが、通常は3のほうが高速で検出結果も維持しやすい。
7. **GPU動画読込(NVDEC)** は既定の `--decoder auto` で自動判定される。ただしBGR画像をCPUへ
   戻す構成のため、PCや動画によってはOpenCVより遅い。本環境の実測ではOpenCVを既定とした。
8. `--stride` はフレーム間引きで速くなるが、追跡が途切れて誤検知・取りこぼしが
   増えるため非推奨。基本は上記で稼ぐ。

## 検出ロジック

次の条件をすべて満たす track を「追い越し」とする（主に横位置 cx で判定）:

1. **車両検出**: 各フレームを YOLO で四輪車両を検出 (car/truck/bus)。NMSはクラス横断
   (`agnostic_nms`)。至近距離の車はcar/truck/busの判定が揺れ、クラス別NMSだと同じ車体に
   箱が2つ残り、ByteTrackが別の車として追跡を分断してしまうため
2. **5 フレーム以上追跡**: ByteTrack で同一車両に ID 付与し、5 サンプル以上
3. **追い越し側から抜けている**: front は右端側(cx ≥ `--appear-edge`)で出現 /
   rear は左端側(cx ≤ 1−`--appear-edge`)で最接近して抜ける(消失点＝中央から現れる)。
   代表位置は1/4区間の中央値だが、抜けたあと前方に映り続ける長い尾で中央寄りへ
   引かれるため、出現直後 `--appear-window-seconds` の間に最も端へ寄った位置も見る
4. **追い越し方向へ移動**: front は右端→中央へ左流れ / rear は中央→左端へ左流れ
   （後方は左右反転のため、前方と逆に中央から端へ向かう）
5. **逆向きに横切る車は除外**: front は左端(cx ≤ `--exit-edge`)で消える車 /
   rear は右端(cx ≥ 1−`--exit-edge`)から現れる車（＝横切り・遠ざかる対向車）を除外
6. **自車運動ゲート**(既定有効): 自転車が**停止中**(背景がほぼ動かない)に
   発生した track を除外。信号待ち・T字路など、停止中に横を通る/陰から現れる車の
   誤検知を抑える。連続フレーム間の背景オプティカルフロー(縮小320px)の中央値を
   自車速度の代理とし、track のフロー中央値が `--stop-flow` 未満なら停止と判定。
   `--no-stop-filter` で無効化。
7. **2次元軌跡フィルタ**: bbox下端中央の縦移動を道路奥行き方向の動きとして扱う。
   横移動だけが大きいtrackを、交差道路を横切る車両として除外する。
8. **面積変化フィルタ**: 後方カメラでは接近に伴う拡大、前方カメラでは離脱に伴う
   縮小を必須とする。変化が逆の車両と、中盤だけ大きくなる横切り車両を除外する。
   ただし最接近時にbboxが画面の8%以上になる**至近通過**は、通過側で大きく映って
   その後縮みながら離れることを確認したうえで、7・8のフィルタを免除する(救済)。
   面積ピークより前のサンプル数は問わない(`--close-pass-min-pre-samples`)。
9. **道路ROI**(任意): `--road-roi` 指定時、bbox下端中央が台形の道路領域内に
   一定割合以上存在することを必須にする。固定カメラ向けで、消失点と道路境界は
   `--vanishing-x`、`--vanishing-y`、`--road-bottom-left`、
   `--road-bottom-right` で調整する。
10. **車種分類**: YOLOのtruck/busは「大型」、carは「普通」とする。追跡区間全体を調べ、
    carの車体下部中央に黄色いナンバー形状が連続フレームで確認できた場合だけ「軽」とする。
    最接近時に側面しか映らない場合も、通過後にナンバーが見えるフレームを利用する。
    逆光・ぼけなどでナンバーが見えない場合に備え、GUIで3分類を手動修正できる。
    GoProの広角歪みで画面端の車両が大きく見えるため、車種投票にはbbox面積を使わず、
    画面端の票を弱くする。truck/bus票が70%以上で複数フレーム続く場合だけ「大型」とし、
    car票が混在するバンは「普通」側へ判定する。大型車の黄色い注意表示で「軽」にならない
    よう、強いtruck/bus判定を覆す場合は黄色ナンバースコア0.75以上を要求する。

各フィルタの診断値はCSVにも出力される。実動画で取りこぼしが増えた場合は、まず
`--min-area-ratio` と `--min-vertical-motion` を小さくして調整する。道路ROIは
GoProの向き・画角で変わるため既定では無効になっている。

> **`--stop-flow` の調整**: 既定 0.8 は撮影の速度・fps・解像度で最適値が変わる。
> まず一度走らせ、CSV の `ego_motion` 列で「走行中の追い越し」と「停止中の誤検知」の
> 値域を見比べ、その中間にしきい値を設定するとよい。
>
> **注意**: 背景フローは少数の移動物体には中央値で頑健だが、追い越し車が画面の
> 大部分を占めるほど近い場合は値が膨らみ、停止中でも走行と誤判定しうる。

## 既知の制約 / 今後

- **離隔距離は未対応**: `peak_bbox_area` は「近さの相対指標」であり実距離(m)ではない。
  単眼カメラから実距離を出すにはカメラ校正＋車幅などの既知サイズが必要。
  正確な離隔距離は超音波/レーダー等のセンサ併用が確実。
- **車線別**: 現状は「left/right(自分から見た側)」のみ。厳密な車線番号には
  路面の車線境界線(レーンマーカー)検出の追加が必要。
- GoPro GPS/IMU(GPMF) テレメトリは自車速度・進路の付加情報として今後連携可能
  (追い越し継続時間や接近相対速度の推定に有用)。
