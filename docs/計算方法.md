# データ算出方法資料

## 1. 算出フロー

本ツールのデータ算出は、次の順で行う。

1. GoPro 動画から追い越し候補を検出する。
2. 候補を目視確認し、採用・除外・車種を確定する。
3. GoPro と LiDAR の時刻オフセットを求める。
4. 採用候補の時刻に対応する LiDAR フレームを開く。
5. 対象車両の点群を矩形選択し、フレーム別に保存する。
6. 各フレームの最近接点から軌跡 CSV を作る。
7. 軌跡からフェーズ、離隔距離、通過時間、相対速度、TTC を算出する。
8. GoPro GPS 速度と統合し、自転車速度・自動車速度を最終 Excel に出力する。

主な実装ファイルは次のとおり。

| 処理 | 実装 |
|---|---|
| 追い越し候補検出 | `detect_overtaking.py` |
| GUI とレビュー保存 | `web_gui.py` |
| GoPro GPS 抽出 | `extract_telemetry.py` |
| GoPro/LiDAR 時刻同期 | `gpmf_sync.py` |
| LiDAR PCAP 読み込み・点群出力 | `lidar_pcap.py` |
| 最近接点 CSV と分析値算出 | `edit_csv.py` |
| 最終 Excel 出力 | `final_export.py` |
| 点群からの車両自動追跡 | `lidar_autotrack.py` |
| 全自動実行（1〜8の通し） | `run_pipeline.py` |
| 手作業の正解データとの照合 | `tools/compare_truth.py` |

全自動実行では 2（目視確認）と 5（矩形選択）を機械が行う。5 は `lidar_autotrack` が
追い越し車らしいトラックを列挙し、`run_pipeline` が「動画の最接近時刻 + 時刻オフセット」
に最も近い車を候補ごとに 1 対 1 で割り当てる。2 はその結果を使って後段で行い、車が
見つからない候補と離隔距離が隣車線相当の候補を除外する（README「イベント↔車両の
割り当て」「自動レビューの判定」）。

## 2. 追い越し候補の検出方法

### 2.1 車両検出と追跡

各フレームに対して YOLO を実行し、`car`、`truck`、`bus` を四輪車両として検出する。検出結果は ByteTrack で同一車両ごとの track にまとめる。

候補にするには、track が次の最低条件を満たす必要がある。

- 5 サンプル以上ある。
- track 継続時間が `--min-track-seconds` 以上である。
- YOLO 検出と追跡が同一車両として維持されている。

### 2.2 位置と移動方向

画面内の車両位置は bbox の中心座標 `cx` と、bbox 下端中央の `bottom_y` を使う。`cx` は画面幅で正規化された 0 から 1 の値である。

track の先頭 1/4 区間と末尾 1/4 区間について中央値を取り、次を算出する。

- `cx_start`: 出現側の代表横位置
- `cx_end`: 消失側の代表横位置
- `y_start`: 出現側の代表 bbox 下端位置
- `y_end`: 消失側の代表 bbox 下端位置
- `area_start`: 出現側の代表 bbox 面積
- `area_end`: 消失側の代表 bbox 面積

撮影方向ごとの追い越し条件は次のとおり。

| 撮影方向 | 追い越し車の想定挙動 | 主な条件 |
|---|---|---|
| 前方 `front` | 画面右端から現れ、中央側へ流れる | `cx_start >= appear_edge` かつ `cx_end < cx_start` |
| 後方 `rear` | 中央付近から現れ、左端へ大きくなりながら流れる | `cx_end <= 1 - appear_edge` かつ `cx_end < cx_start` |

横切り車両や対向車のような逆方向の動きは、`exit_edge` によって除外する。

### 2.3 自車運動ゲート

停止中に横を通る車両や、交差点で現れる車両を追い越しとして誤検出しないよう、背景のオプティカルフローを自車運動の代理値として使う。

連続フレーム間で背景特徴点の移動量を求め、track 区間内の中央値を `ego_motion` とする。`ego_motion < stop_flow` の場合、自転車が停止中とみなして候補から除外する。

このフィルタは既定で有効であり、`--no-stop-filter` で無効化できる。

### 2.4 軌跡フィルタ

bbox 下端中央の縦方向変化を、道路奥行き方向の移動として扱う。

```text
front: vertical_motion = y_start - y_end
rear : vertical_motion = y_end - y_start
lateral_motion = |cx_end - cx_start|
lateral_vertical_ratio = lateral_motion / max(|y_end - y_start|, 1e-6)
```

`vertical_motion < min_vertical_motion` の場合は、奥行き方向の動きが不足しているとして除外する。`lateral_vertical_ratio > max_lateral_vertical_ratio` の場合は、横方向主体の交差交通として除外する。

### 2.5 面積変化フィルタ

追い越し車は、撮影方向によって bbox 面積の変化方向が異なる。

```text
front: area_change_ratio = area_start / area_end
rear : area_change_ratio = area_end / area_start
```

`area_change_ratio < min_area_ratio` の場合は、接近・離脱に伴う面積変化が不足しているため除外する。

また、track 中盤だけ bbox が大きくなる横切り車両を除外するため、最大面積が中盤にあり、次の値が `max_mid_peak_ratio` を超える場合も除外する。

```text
mid_peak_ratio = peak_area / max(area_start, area_end)
```

### 2.6 道路 ROI

`--road-roi` を指定した場合、bbox 下端中央が台形の道路 ROI 内にある割合 `road_ratio` を計算する。`road_ratio < min_road_ratio` の track は除外する。

道路 ROI は GoPro の取り付け位置や画角に依存するため、既定では無効である。

## 3. 車種分類

車種は `大型`、`普通`、`軽` の3分類で扱う。

基本判定は次のとおり。

- YOLO が `truck` または `bus` と判定したフレームが一定以上続く場合は `大型`。
- YOLO が `car` と判定した場合は原則 `普通`。
- `car` の車体下部中央に黄色ナンバー形状が連続フレームで確認できた場合は `軽`。

画面端では GoPro の広角歪みにより車両が大きく見えやすいため、車種投票には bbox 面積を使わない。画面端の投票は弱く補正される。

大型車の黄色い注意表示などを軽と誤判定しないよう、`truck` / `bus` の強い判定を軽へ上書きする場合は、通常より高い黄色ナンバースコアを要求する。

### 3.1 点群の寸法による決め直し（全自動時）

全自動パイプラインでは、LiDAR で車両を追跡できた行の車種を上の動画判定ではなく
**点群で測った車体寸法**で決め直す（`run_pipeline.lidar_vehicle_class`、段階6a）。
動画側の判定は次の2方向に外れるためで、実データ 260701 の正解45件では 27/45 しか当たらない。

- ミニバン・ワゴン・ハイエースを YOLO が `truck` と呼ぶ（普通 → 大型 の誤り）
- トラック後部の黄色い標示・反射板を軽の黄色ナンバーと見る（大型 → 軽 の誤り）

使う寸法は追跡クラスタの外接矩形（`lidar_autotrack.TrackSummary`）で、いずれも
トラック全体の 80 パーセンタイル。

| 名前 | 意味 |
|---|---|
| `length` | Y 方向（進行方向）の広がり ＝ 車体長 |
| `width` | X 方向（横方向）の広がり ＝ 車幅 |
| `height` | 地面平面からの上端高 ＝ 車高（地面除去の上限 3.0m で頭打ち） |

判定は次の順。

1. **大型**: `車体長 × 車高 >= 9.0 m²`（側面のシルエット面積）。
   大型車は長さと高さの**両方**が大きいので、片方だけのしきい値より素直に分かれる。
2. **軽**: `2.50m <= 車体長 <= 3.50m` かつ `1.20m <= 車幅 <= 1.80m`。
   軽自動車の規格は 3.40m × 1.48m。上限はクラスタの外接矩形が 0.4m グリッド分
   ふくらむ分を足した値。下限は「車の全体を測れていない測定値を軽と呼ばない」ため。
3. それ以外は **普通**。

車を割り当てられなかった行と、人がレビューで車種を直した行（`class_reviewed`）、
LiDAR 発の「未確認」行（車種は空欄）は書き換えない。

しきい値の根拠（260701 の正解45件、`--auto-offset`）:

- 側面積: 実測は 軽 4.5〜9.0 / 普通 2.7〜10.1 / 大型 4.4〜37.6 m²。
  9.0 で 39/45。8.5 で 36、9.5 で 38、10.0 以上では 36〜37 に落ちる
  （上へ動かすと大型を取りこぼす。下へ動かすと普通・軽を大型と呼ぶ）
- 軽の車体長上限: 正解が軽の行の実測は 3.14〜3.43m、普通の行は 3.53m 以上。
  3.44〜3.62m のどこでも成績は同じで、3.50 はその中央
- 軽の車幅上限: 軽は 1.49〜1.77m、次に大きい普通が 1.86m。1.72〜1.86m で同成績
- 下限（2.50m / 1.20m）: 1.50〜3.10m / 0.50〜1.45m で同成績。追跡が車の一部しか
  掴めなかった行（例: 1.68m × 0.72m）を軽と呼ばないためだけの安全弁

**過学習の確認**: セッションを1つ抜いて残り4つでしきい値を選び、抜いたセッションで
測る交差検証では 37/45（動画のみ 27/45、全データで決めた既定値は 39/45）。
選ばれるしきい値も 9.0 / 3.38〜3.46 / 1.68〜1.72 と 5 回ともほぼ同じだった。

## 4. 追い越し候補 CSV の時刻

`overtaking_events.csv` には、次の時刻が出力される。

| 列 | 意味 |
|---|---|
| `t_start_s` | 連結タイムライン上の候補開始時刻 |
| `peak_t_s` | bbox 面積が最大になる最接近目安時刻 |
| `t_end_s` | 連結タイムライン上の候補終了時刻 |
| `duration_s` | `t_end_s - t_start_s` |
| `source_video` | 候補が検出された元動画 |
| `local_t_start_s` | 元動画内の候補開始時刻 |
| `local_t_end_s` | 元動画内の候補終了時刻 |

複数動画をまとめて処理する場合、`t_*_s` は先頭動画からの累積時間、`local_*_s` は個別動画内の時刻になる。

## 5. GoPro と LiDAR の時刻同期

GoPro 動画内の GPMF から GPS UTC タイムスタンプ `GPSU` を読み取り、GPMF サンプルの presentation time を差し引いて、動画 `t=0` の UTC を推定する。

```text
GoPro開始Unix時刻 = GPSUのUnix時刻 - GPMFサンプル時刻
```

複数サンプルから推定値を作り、中央値付近の安定したクラスタを使う。

LiDAR 側は PCAP の最初のパケット時刻を開始 Unix 時刻とする。

GUI で使うオフセットは次で算出する。

```text
offset = GoPro開始Unix時刻 - PCAP開始Unix時刻
```

この実装では、レビュー済み CSV の VeloView 表示時刻は次で作る。

```text
VeloView時刻 = GoPro候補時刻 + offset
```

最終 Excel で GoPro GPS 速度を参照する際は、LiDAR 側の時刻を GoPro 動画内時刻へ戻すために、offset と複数動画の累積オフセットを差し引く。

```text
GoPro動画内時刻 = LiDAR相対時刻 - offset - 動画累積オフセット
```

## 6. LiDAR 点群の座標算出

PCAP から Velodyne の標準 1206-byte データパケットを読み込み、距離、方位角、垂直角から点群座標を算出する。

距離は Velodyne の raw distance を 0.002 倍して m に変換する。

```text
distance = distance_raw * 0.002
horizontal = distance * cos(vertical_angle)
X = horizontal * sin(azimuth)
Y = horizontal * cos(azimuth)
Z = distance * sin(vertical_angle)
```

対応する垂直角テーブルは LiDAR モデルごとに切り替える。

- VLP-16
- HDL-32E
- VLP-32C

GUI で矩形選択した範囲は、次の条件で点を抽出する。

```text
min_x <= X <= max_x
min_y <= Y <= max_y
laser指定がある場合は laser_id が指定集合に含まれる
```

出力 CSV では、選択点ごとに距離、方位角、仰角、`Points:0`、`Points:1`、`Points:2` を保存する。

```text
Distance = sqrt(X^2 + Y^2 + Z^2)
Azimuth = atan2(X, Y)
Elevation = atan2(Z, sqrt(X^2 + Y^2))
```

## 7. 最近接点 CSV の算出

`overtaking_XXX.csv` には、各フレームで選択された複数点が含まれる。`edit_csv.py` は各フレームから、XY 平面上で自転車に最も近い点を1点選ぶ。

```text
distance(m) = sqrt(X^2 + Y^2)
最近接点 = distance(m) が最小の点
```

### 7.1 路面点の除去

矩形選択の範囲は車両の外接箱に余裕（`lidar_autotrack.BOX_MARGIN` = 0.3 m）を足したものなので、車体の左右外側の路面がわずかに範囲へ入り込む。この路面点が最近接点になると、離隔距離 LC が車体までの距離より小さく出る。

そこで最近接点を選ぶ前に、フレームごとに路面付近の点を落とす。

```text
路面高さ = そのフレームの Z の下側 2 パーセンタイル
除外対象 = Z < 路面高さ + 0.10 m の点
```

点数が 30 未満のフレームは路面高さを推定できないため何もしない。除外すると点が 1 つも残らない場合も、車両を見失うより路面が混じるほうが安全なため元の点を使う。

パラメータは `edit_csv.py` の `GROUND_PERCENTILE` / `GROUND_MARGIN` / `GROUND_MIN_POINTS` である。ID1 の正解 12 件との照合では、除去なしで LC の平均絶対差 0.550 m（対応の確かな 8 件では 0.227 m、系統的に 0.23 m 小さめ）だったものが、除去ありで 0.478 m（同 8 件では 0.122 m、偏り −0.11 m）へ改善する。パーセンタイルを 0〜10 %、余裕を 0.05〜0.30 m の範囲で変えても確実な 8 件の平均絶対差は 0.12 m でほぼ一定であり、値の選び方に敏感ではない。ID3（対応 9 件）では LC の平均絶対差 0.771 m → 0.770 m とほぼ変わらず、通過時間が 0.611 秒 → 0.589 秒へわずかに改善する。ID3 は車両割り当ての精度自体が低く（再現率 10/14、余剰 22 件）、LC の誤差はそちらが支配的である。

### 7.2 自車構造物の除去と軌跡の連続性

LiDAR は自転車に載っているので、原点のごく近くには常に自車側の点（センサ架台と搭乗者）が返ってくる。追い越し車が真横を通り過ぎると車までの距離がこの自車構造物より遠くなり、最近接点が自車構造物へ乗り移って軌跡がそこで止まってしまう。こうなると `|Y|` が 3 m へ戻らないためフェーズ4が作れず、フォールバックで最終点をフェーズ4に代用した結果、通過時間が数秒に伸び距離 p3・相対速度・TTC が符号ごと壊れる。実データでは ID3 候補056（TTC −17.2 秒、距離 p3 −0.95 m）と ID4 候補011（通過時間 6.2 秒、TTC 10.7 秒）がこれで壊れていた。

そこで最近接点の選び方に次の3つを足す。

1. **架台そのものを外す**: `distance(m) < EGO_MIN_DISTANCE`（0.8 m）の点を候補にしない。ID1〜ID5 の edit CSV 全 10418 点のうち 1.2 m 未満は 224 点あり、その 223 点が 0.48〜0.50 m に密集する。0.5〜1.0 m には 1 点も無いので、このギャップに置いた 0.8 m は VLP-16 の最小測距の内側にある自車構造物だけを落とす。
2. **通過側でない点を外す**: 追い越し車は車体まるごと通過側（日本の右側追い越しなら X > 0）にあるので、反対側の点は搭乗者・自転車・対向物である。通過側は `|Y| >= 3 m`（自車構造物が届かない遠方）のフレームの最近接点の X の符号の多数決で決める。多数派が `PASSING_SIDE_MIN_RATIO`（0.6）に満たなければ側による除去はしない。搭乗者の体は 0.8〜2 m にも点を返し距離では車と区別できないが、この規則なら落とせる。
3. **軌跡を1本の鎖としてつなぐ**: フレームごとに独立に最近接点を選ぶのをやめ、まず 1・2 を適用した最近接点の列を「隣り合うフレームの移動が `MAX_STEP_SPEED_MPS`（30 m/s）以内」で区間に切り分け、**最長区間の最接近フレーム**を起点にする。そこから前後へ、同じ 30 m/s の条件を満たす最も近い点だけを順につないでいく。つなげなくなったらそこで打ち切り、残りのフレームは空欄にする。最近接点は車体上を移り変わるので車速よりずっと速く動くことがあり（実データの接近区間で最大 75 km/h ≒ 21 m/s）、30 m/s はその外側に置いた。「一番近いフレーム」ではなく「最長区間」を起点にするのは、車が通り過ぎた後に数フレームだけ最近接になる自車構造物を掴まないためである。

なお 3 の打ち切りは「追い越し車は追跡窓の途中で消えない」という前提に立つ。フェーズ4より後ろの点は分析に使わないので、打ち切りが早すぎても指標には影響しない。

ID1・ID3・ID4 を再実行して正解と照合すると、再現率・重複出力・余剰行・車種一致はすべて変わらず、指標の平均絶対差は次のようになる。値が変わる対応行は ID3 候補056 と ID4 候補011 の 2 件だけで、他の 28 行は最大 0.04 m の差に収まる。

| 指標 | ID1 前→後 | ID3 前→後 | ID4 前→後 |
|---|---|---|---|
| 離隔距離 LC [m] | 0.509 → 0.513 | 0.480 → 0.480 | 0.385 → **0.371** |
| 通過時間 [s] | 0.191 → 0.191 | 0.645 → **0.418** | 0.963 → **0.350** |
| 距離 p2 [m] | 1.494 → 1.494 | 1.875 → 1.875 | 1.318 → 1.318 |
| 距離 p3 [m] | 0.865 → 0.865 | 1.495 → **1.053** | 0.841 → **0.743** |
| 相対速度 [km/h] | 2.699 → 2.699 | 4.008 → **3.018** | 3.599 → **2.488** |
| TTC [s] | 0.346 → 0.346 | 2.173 → **0.547** | 1.514 → **0.403** |

ID1 の LC がわずかに悪化するのは、候補007 の通過区間で自車構造物に乗っ取られていたフレームが車の点に戻り、そのうち 1 点（1.023 m）が従来より近かったためである（正解 1.06 m、誤差 0.00 → 0.04 m）。ID2・ID5 では対応行の値は変わらない。

出力される `overtaking_XXX_edit.csv` の列は次のとおり。

| 列 | 意味 |
|---|---|
| `unixtime` | LiDAR フレーム時刻。PCAP 内の相対秒、または元 CSV の時刻文字列。 |
| `X` | 最近接点の X 座標 |
| `Y` | 最近接点の Y 座標 |
| `Z` | 最近接点の Z 座標 |
| `distance(m)` | `sqrt(X^2 + Y^2)` |
| `speed(km/h)` | 前フレーム最近接点からの移動速度 |

速度は前フレームの最近接点との差分から算出する。

```text
speed(km/h) = sqrt((X_i - X_{i-1})^2 + (Y_i - Y_{i-1})^2)
              / (t_i - t_{i-1}) * 3600 / 1000
```

先頭フレームの速度は空欄になる。有効点がないフレームでは、時刻以外は空欄になる。

### 7.3 追跡が通過区間の途中で切れる問題（クラスタの分離）

追い越し車が真横に並ぶと、車体と自転車・搭乗者の隙間が 1m 弱まで詰まる。点群の
クラスタリングは 0.4m グリッドを ``LINK_CELLS`` = 2 セル（0.8m）の隙間まで繋ぐので、
このとき車と自車側の点が 1 つのかたまりになる。かたまりは点数の多い自車側の
トラックに取られるため、**車のトラックがちょうど通過の瞬間に切れる**。

追跡が切れると `overtaking_XXX.csv` は通過区間を抜ける前で終わり、フェーズ4が
代用点（8.1）になる。結果として通過時間・距離p3・相対速度・TTC が同時に壊れる。

対策として、1 台の車としてありえない大きさ（`lidar_autotrack.SPLIT_MAX_WIDTH` = 4.0m ×
`SPLIT_MAX_LENGTH` = 20.0m の外接矩形を超える）になったかたまりだけ、連結を 1 セル
狭めてほどき直す（2 つ以上に分かれたときだけ採用するので、本当に大きな 1 物体は
そのまま残る）。しきい値は `score_track` が「車両らしくない」と判定する寸法と同じ値。

260701 の全5セッション（`--auto-offset`、正解45件）での効果:

| 指標 | 分離なし | 分離あり |
|---|---|---|
| 離隔距離 LC [m] | 0.337 | **0.247** |
| 通過時間 [s] | 0.358 | **0.253** |
| 距離 p3 [m] | 1.202 | **0.633** |
| 相対速度 [km/h] | 2.847 | **1.862** |
| TTC [s] | 0.366 | **0.350** |
| 余剰行 | 80 | **75** |

### 7.4 通過時刻をどの滞在で決めるか

トラックが通過区間（`|Y| < 3m`）へ 2 回以上入ることがある。路肩の静止物を追って
いたトラックが、後ろから来る追い越し車へ乗り移ると起きる（`MAX_SPEED_REVERSAL` は
速度差の大きい乗り移りしか止められず、ゆっくり近づく車への乗り移りは同じ物体でも
起きる見かけの揺り戻しと区別できない）。最初の滞在を通過時刻にすると数秒早くなり、
イベントとの割り当てが外れて車を丸ごと落とす。

そこで、**矩形が `Y = 0` を跨いだ滞在**（＝自転車の真横に並んだ滞在）を通過とみなす
（`lidar_autotrack._passing_visit`）。区間へ 1 回しか入らないふつうのトラックでは
最初の滞在がそのまま選ばれるので、値は 1 つも変わらない。

260701/ID5 の 574.3s はこれで回収した（路肩の物体が `|Y| = 2m` をかすめた 567.4s が
通過時刻になっていた。修正後の通過時刻 573.9s、正解 574.3s）。

## 8. フェーズ分類

`edit.csv` の有効点から、次の4フェーズを決める。

| フェーズ | 定義 |
|---|---|
| フェーズ1 | 最初の有効点 |
| フェーズ2 | `abs(Y) < 3` になる前かつ `abs(Y) <= 5.5` の点のうち、速度が一桁 km/h の最後の点。該当がなければ速度の絶対値が最小の点。 |
| フェーズ3 | フェーズ2以降で `abs(Y) < 3` になった最初の点。 |
| フェーズ4 | フェーズ3以降で `abs(Y) >= 3` になった最初の点。 |

3m は、車両が自転車に近接して通過している区間を Y 方向の位置で切り出すためのしきい値として使われる。`distance(m)` は `sqrt(X^2 + Y^2)` であり、フェーズ3・4の判定には使わない。

フェーズ2は、車両が近接区間に入る前の基準点として扱う。実装では、`abs(Y) < 3` になった時点で候補探索を打ち切り、それより前に速度値が入っている点だけをフェーズ2候補にする。候補の中に `0 <= abs(speed) < 10` の点がある場合は、その最後の点をフェーズ2にする。該当する一桁速度の点がない場合は、速度の絶対値が最も小さい点をフェーズ2にする。

最近接点が車体上を移り変わると `speed(km/h)` にスパイクが出るため、フェーズ2候補は速度の絶対値が 100 km/h 以下の点に限定する。除外した点があった場合は品質警告を残す。候補がすべて 100 km/h を超える場合は、値を変えないよう制限前の候補から選び直したうえで警告する。

さらにフェーズ2候補は `abs(Y) <= 5.5 m`（`edit_csv.PHASE2_MAX_ABS_Y`）の点に限定する。速度が一桁の点が無いときの規則「速度の絶対値が最小の点」は、追跡区間が長いほど遠方の点を拾ってしまい、`distance_p2` と TTC が系統的に過大になるためである。`abs(Y) <= 5.5 m` の候補が1点も無い場合は制限を外して選び直し、品質警告を残す。

上限値は ID1 の正解 12 件（時刻対応が付いた 10 件）との照合で決め、閾値決めに使っていない ID3（対応 9 件）で確認した。上限を変えたときの `distance_p2` の平均絶対差は次のとおりである。

| 上限[m] | 4.0 | 4.5 | 5.0 | 5.25 | 5.5 | 6.0 | 7.0 | 8.0 | 上限なし |
|---|---|---|---|---|---|---|---|---|---|
| ID1 (n=10) | 1.76 | 1.76 | 1.76 | 1.42 | 1.42 | 1.53 | 1.78 | 1.78 | 6.32 |
| ID3 (n=9) | 2.35 | 2.16 | 1.84 | 1.74 | 1.46 | 1.46 | 1.28 | 1.28 | 6.43 |
| 合算 (n=19) | 2.04 | 1.95 | 1.80 | 1.57 | **1.44** | 1.49 | 1.55 | 1.55 | 6.37 |

合算で最小になる 5.5 m を採用した。TTC の平均絶対差も同様に下がる（ID1 1.06 秒 → 0.28 秒、ID3 13.1 秒 → 2.44 秒）。ID1 で 1 件を除いて選び直すジャックナイフでも 10 回中 9 回この付近が最良となる。上限の付近では値が平らなので、4〜7 m のどこを選んでも上限なしより大きく改善する。

フェーズ2は `distance_p2` と TTC の算出に使う。

```text
distance_p2 = abs(Y_phase2)
TTC = abs(Y_phase2) / (relative_speed / 3.6)
```

### 8.1 フェーズが見つからない場合のフォールバック

全自動処理では、途中で例外停止すると人が異常に気づけないため、`analyze_edit_points` は可能な範囲で計算を続け、代用した内容を品質警告として返す。警告は最終 Excel 生成時の `warnings` に流れる。

| 状況 | 動作 |
|---|---|
| フェーズ2が無い（`abs(Y) < 3` になる前に速度値のある点が無い） | フェーズ3直前の有効点をフェーズ2として代用し、警告を残す |
| フェーズ4が無い（フェーズ3以降で `abs(Y) >= 3` に戻らない） | 最終有効点をフェーズ4として代用し、警告を残す |
| フェーズ3が無い（`abs(Y) < 3` の点が1つも無い） | 通過区間を作れず計算不能。点群の選択範囲・同期ずれの可能性を示す例外で停止する |
| フェーズ4が無く、かつフェーズ3が最終点 | 通過区間の長さが 0 になるため例外で停止する |
| 相対速度が 0 以下（フェーズ4がフェーズ3より手前） | 計算は続けるが、追い越し車以外を追跡している疑いとして警告を残す |

`classify_phases(points, strict=True)`（既定）は従来どおり、フェーズ2・フェーズ4が無い場合も例外を送出する。フォールバックを使うのは `strict=False` のときだけである。

## 9. 分析指標の算出式

フェーズ分類後、次の指標を算出する。

### 9.1 離隔距離 LC

フェーズ3からフェーズ4までの区間を通過区間とする。そのうち `distance(m) >= 1.0` の点があればその点群を対象にし、なければ通過区間全体を対象にする。

`X` は横方向の座標であり、通過区間の X は本来、車が抜けていった側の符号に偏る。1点だけ反対符号の外れ値が混ざると最小値がその点で決まってしまうため、点数の多い側（同数なら X の合計の符号＝重心の側）を通過側とし、その符号の点だけを対象にする。除外した点があった場合は品質警告を残す。

```text
通過側 = X が正の点数と負の点数の多い方（同数なら sum(X) の符号）
LC = min(abs(X))   ただし通過側の点のみ
```

LC は「通過側で最も近い横距離」である。

> 旧実装は対象区間の符号付き最小値を用いて `LC = abs(min(X))` としていた。これは X が正側（通過側が X > 0）のときだけ最も近い横距離になり、X が負側のときは逆に最も遠い横距離を返していた。現在は左右どちらの側でも最も近い横距離を返す。

### 9.2 通過時間

```text
passing_time = t_phase4 - t_phase3
```

単位は秒。

### 9.3 距離 p2

```text
distance_p2 = abs(Y_phase2)
```

単位は m。

### 9.4 距離 p3

```text
distance_p3 = Y_phase4 - Y_phase3
```

単位は m。フェーズ3からフェーズ4までの Y 方向の移動量として扱う。

### 9.5 相対速度

```text
relative_speed(km/h) = distance_p3 / passing_time * 3.6
```

### 9.6 TTC

```text
TTC(s) = abs(Y_phase2) / (relative_speed / 3.6)
```

相対速度が 0 の場合、TTC は算出不能値になる。

## 10. GoPro GPS 速度の算出

GoPro の GPMF `GPS5` から GPS 速度を抽出し、`telemetry_gps.xlsx` を作成する。

主に使用する列は次のとおり。

- `cts`: GoPro 動画内時刻
- `GPS (2D speed) [m/s]`: 2D 速度

最終 Excel では、フェーズ3からフェーズ4までの GoPro 動画内時刻範囲に含まれる GPS 速度を平均し、km/h に変換する。

```text
bicycle_speed(km/h) = average(GPS 2D speed [m/s]) * 3.6
```

対象範囲に GPS 速度がない場合、自転車速度は空欄になる。

## 11. 自動車速度の算出

自動車速度は、自転車速度と LiDAR から求めた相対速度の和として出力する。

```text
vehicle_speed(km/h) = bicycle_speed(km/h) + relative_speed(km/h)
```

自転車速度または相対速度が欠けている場合、自動車速度は空欄になる。

## 13. 制約と確認ポイント

- GoPro の bbox 面積だけでは実距離を算出しない。距離・速度の最終算出には LiDAR 点群を使う。
- LiDAR の矩形選択がずれると、最近接点、LC、速度が直接ずれる。
- フェーズ3・4は `abs(Y) = 3m` のしきい値で決まるため、点群選択範囲と外れ値に注意する。
- GPS 速度は GoPro 側の記録に依存する。GPS が欠落している区間では自転車速度と自動車速度が空欄になる。
- 時刻同期の offset がずれると、候補時刻、LiDAR フレーム、GPS 速度参照範囲がすべてずれる。
- TTC は相対速度から計算した目安であり、相対速度が小さい場合や符号が不安定な場合は解釈に注意する。
