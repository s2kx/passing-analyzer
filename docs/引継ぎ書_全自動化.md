## 1. プロジェクトの目標と現在地

GoPro動画とVelodyne LiDAR(PCAP)から自転車追い越し時の離隔距離・速度を算出する本ツールを、
GUIの手作業（クリップ目視確認・点群の矩形選択・メタ情報入力）なしで最終Excelまで通す
**全自動化**が目標。

**現在地（mainブランチ bd10876、第2波完了）**: `run_pipeline.py` にセッションフォルダを
渡すだけ（撮影方向の指定すら不要）で、動画検出→GPS同期→点群自動追跡→自動レビュー→
最終Excelまで人手ゼロで到達する。残る人手は「危険感」の記入と、レポートが挙げる
少数の要確認項目のみ。

## 2. 確定済みの決定事項（ユーザー承認済み）

| 事項 | 決定 |
|---|---|
| 危険感（danger_level） | 全自動時は**空欄**。`DANGER_BY_LEVEL["0"]=""`。人が後から最終Excelへ記入 |
| 離隔距離LCの定義 | 通過側の点群に限定した min(\|X\|)（新定義）。旧 `abs(min(X))` は X<0 側で最遠点を返すバグだったが、**実データの右側追い越しは全て X>0 のため過去データへの影響なし**を確認済み |
| 撮影方向 | 明示指定 > metadata.json > 自動判定（`detect_view.py`）。260701データは**すべて前向き(front)** |
| サブエージェント運用 | メイン=Fable、実装エージェント=Opus 5、worktree分離、完了後メインが統合・回帰テスト |

## 3. 実装の全体像（第1波・第2波で追加したもの）

| ファイル | 役割 |
|---|---|
| `run_pipeline.py` | 全自動パイプライン本体。段階0撮影方向→1検出→2GPS抽出→3時刻同期→4点群追跡→5edit CSV→6自動レビュー→7最終Excel→8レポート(`pipeline_report.json/.txt`)。中断時もレポートは必ず残る |
| `lidar_autotrack.py` | 点群の車両自動追跡（手動矩形選択の代替）。地面平面フィット→XYグリッドクラスタリング→等速度予測トラッキング→追い越し同定→フレーム別bounds生成。約17ms/フレーム。閾値はファイル冒頭の定数群 |
| `detect_view.py` | 撮影方向の自動判定。**背景オプティカルフローの放射方向**（front=消失点から拡散/rear=収縮）。実データ9/9正解・GPU不要・最短1.3秒。「両方向で検出して件数比較」は**誤判定するので判定に使わない**（逆方向設定は誤検知を量産して件数が多くなる。回帰テストで固定済み） |
| `edit_csv.py`（改修） | フェーズ判定フォールバック（フェーズ2/4欠落時は代用点+警告、strict=Trueで従来互換）、LCの通過側限定、速度スパイク検知 |
| `test_pipeline.py` / `test_autotrack.py` / `test_detect_view.py` | 新規テスト。既存 `test_logic.py`・`web_gui.py --check` と合わせて5系統 |

### 点群追跡のプラグイン契約（重要・変更時は後方互換必須）
```python
track_overtaking(pcap, first_frame, last_frame, side="right",
                 expected_pass_time=None, exclude_track_keys=None) -> {
    "ok", "frames": [{"index", "bounds": {min_x,max_x,min_y,max_y}}],
    "confidence", "warnings", "pass_time", "track_key",
    "candidates": [{"track_key","pass_time","score","median_x","lc_estimate"}]}
```
- 呼び出し側（run_pipeline）は `peak_t_s + offset` を期待通過時刻として渡し、
  時刻順グリーディ割り当て＋使用済みtrack_key除外で「1台=1イベント」を保証する
- side は動画CSVの値でなく常に `"right"` を渡す（日本は右側通過=+X。動画側の
  side列は front→"left"/rear→"right" の互換表記で物理と不一致）

### 座標系・同期の要点
- センサ座標: 右側通過=+X、対向車線=-X、前方=+Y、通過区間=|Y|<3m
- offset の定義: `pcap時刻 = gopro時刻 + offset`（`gpmf_sync.compute_gps_offset`）
- ID1 実測 offset = **-58.827秒**、PCAP開始unix = 1782868176.920306
- 追跡窓: front=開始-8s/終了+3s、rear=逆、方向未確定(fallback)時は**両側8sの対称**
  （第2波統合時に見つけた衝突の修正。コミット bd10876 参照）

## 7. 環境の注意点（ハマりどころ）

1. **gitの所有者チェック**: リポジトリの所有Windowsユーザーが違うと
   `dubious ownership` で全git操作が失敗。
   `git config --global --add safe.directory '<リポジトリパス>'` で解消
2. **git識別**: `git config user.name / user.email` をリポジトリローカルに設定しないと
   コミット不可（このPCでは設定済み。別PCでは要設定）
3. **portable python の罠**: `portable\python` は embeddable 版で `._pth` に
   **本体チェックアウトの絶対パスが焼き込まれている**。worktree内で実行すると
   共有側のモジュールを読むため、**テストは `.venv\Scripts\python.exe` で実行**し、
   実データ処理（torch必要）だけ `portable\python\python.exe` を使う
4. GPU: このPCは RTX 4090（動画3本+PCAP1.4GBの全処理6分）。GPUなしでも動くが検出が遅い
5. 検証コマンド一式:
   ```powershell
   .venv\Scripts\python.exe test_logic.py
   .venv\Scripts\python.exe test_autotrack.py
   .venv\Scripts\python.exe test_pipeline.py
   .venv\Scripts\python.exe test_detect_view.py
   .venv\Scripts\python.exe web_gui.py --check
   ```
6. worktree並行開発の教訓: 複数エージェントが `run_pipeline.py` を触ると統合が重い。
   マージベースが古い場合は **ブランチのマージではなく作業コミット単体の cherry-pick**
   が競合を最小化する（第2波Dで実績）。統合後は必ず全テスト＋ID1受け入れ再実行
