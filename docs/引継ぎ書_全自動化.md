## 1. プロジェクトの目標と現在地

GoPro動画とVelodyne LiDAR(PCAP)から自転車追い越し時の離隔距離・速度を算出する本ツールを、
GUIの手作業（クリップ目視確認・点群の矩形選択・メタ情報入力）なしで最終Excelまで通す
**全自動化**が目標。

**現在地（第4波完了・main統合済み、2026-09-01）**: 全5IDの確定実行で
**再現率45/46・重複0・LC平均絶対差0.247m・TTC 0.350s・車種一致39/45**
（唯一の未対応は正解データ自体の重複行。§11・§12参照）。
時刻同期の系統ずれ（+4.2〜5.2秒、LiDAR収録PCの時計ドリフト）が判明したため
時刻オフセットは第5波Pで**自己検証の推定値を既定採用**にした（`--auto-offset` の付け忘れで
全体が数秒ずれる事故を無くすため。§15）。`--skip-detect` 時は `--view front` が必須（§5注意書き）。
残る人手は「危険感」の記入（採用120行）と未確認行の目視確認（16行）のみで、
チェックリストを `output\w4\人手作業チェックリスト.md` に生成済み。
GUIは半自動モード+進捗/中止+撮影方向自動判定ボタンまで完備。
第5波Nで結果閲覧用のHTMLレポート（段階7b `make_report.py` → `out\report.html`）を追加し、
動画の切り抜きと切り抜いた点群をブラウザで確認できるようにした（§13）。
第5波Oで自動レビューに誤検知の足切り（停止中・旋回中・離隔距離2.6m超・追跡の切れ）を
追加した。ID1の再判定では採用20件（うち誤り9）が採用11件（誤り0）になる（§14）。
ID2〜ID5でも確認済み（正解34件中33件を採用、新しい判定で落とした正解は0件。§14）。
残課題は§12末尾の申し送り（ID3 634.2sの追跡短縮、gpmf_sync恒久是正など）。

## 3. 実装の全体像（第1波・第2波で追加したもの）

| ファイル | 役割 |
|---|---|
| `run_pipeline.py` | 全自動パイプライン本体。段階0撮影方向→1検出→2GPS抽出→3時刻同期→4点群追跡→5edit CSV→6自動レビュー→7最終Excel→8レポート(`pipeline_report.json/.txt`)。中断時もレポートは必ず残る |
| `lidar_autotrack.py` | 点群の車両自動追跡（手動矩形選択の代替）。地面平面フィット→XYグリッドクラスタリング→等速度予測トラッキング→追い越し同定→フレーム別bounds生成。約17ms/フレーム。閾値はファイル冒頭の定数群 |
| `detect_view.py` | 撮影方向の自動判定。**背景オプティカルフローの放射方向**（front=消失点から拡散/rear=収縮）。実データ9/9正解・GPU不要・最短1.3秒。「両方向で検出して件数比較」は**誤判定するので判定に使わない**（逆方向設定は誤検知を量産して件数が多くなる。回帰テストで固定済み） |
| `edit_csv.py`（改修） | フェーズ判定フォールバック（フェーズ2/4欠落時は代用点+警告、strict=Trueで従来互換）、LCの通過側限定、速度スパイク検知 |
| `make_report.py` | 結果閲覧用HTMLレポート（段階7b）。動画クリップの相対参照と点群ビューア（上面図・側面図・フレーム送り）を1枚のHTMLにまとめる。単体CLIで既存出力から再生成できる。§13 |
| `test_pipeline.py` / `test_autotrack.py` / `test_detect_view.py` / `test_make_report.py` | 新規テスト。既存 `test_logic.py`・`web_gui.py --check` と合わせて6系統 |

### 点群追跡のプラグイン契約（重要・変更時は後方互換必須）
```python
track_overtaking(pcap, first_frame, last_frame, side="right",
                 expected_pass_time=None, exclude_track_keys=None) -> {
    "ok", "frames": [{"index", "bounds": {min_x,max_x,min_y,max_y}}],
    "confidence", "warnings", "pass_time", "track_key",
    "candidates": [{"track_key","pass_time","score","median_x","lc_estimate"}]}
```
- 呼び出し側（run_pipeline）は `peak_t_s + offset` を期待通過時刻として渡し、
  時刻順グリーディ割り当て＋使用済みtrack_key除外で「1台=1イベント」を保証する
- side は動画CSVの値でなく常に `"right"` を渡す（日本は右側通過=+X。動画側の
  side列は front→"left"/rear→"right" の互換表記で物理と不一致）

### 座標系・同期の要点
- センサ座標: 右側通過=+X、対向車線=-X、前方=+Y、通過区間=|Y|<3m
- offset の定義: `pcap時刻 = gopro時刻 + offset`（`gpmf_sync.compute_gps_offset`）
- ID1 実測 offset = **-58.827秒**、PCAP開始unix = 1782868176.920306
- 追跡窓: front=開始-8s/終了+3s、rear=逆、方向未確定(fallback)時は**両側8sの対称**
  （第2波統合時に見つけた衝突の修正。コミット bd10876 参照）

## 7. 環境の注意点（ハマりどころ）

1. **gitの所有者チェック**: リポジトリの所有Windowsユーザーが違うと
   `dubious ownership` で全git操作が失敗。
   `git config --global --add safe.directory '<リポジトリパス>'` で解消
2. **git識別**: `git config user.name / user.email` をリポジトリローカルに設定しないと
   コミット不可（このPCでは設定済み。別PCでは要設定）
3. **portable python の罠**: `portable\python` は embeddable 版で `._pth` に
   **本体チェックアウトの絶対パスが焼き込まれている**。worktree内で実行すると
   共有側のモジュールを読むため、**テストは `portable\python\python.exe` で実行**し、
   実データ処理（torch必要）だけ `portable\python\python.exe` を使う
4. GPU: このPCは RTX 4090（動画3本+PCAP1.4GBの全処理6分）。GPUなしでも動くが検出が遅い
5. 検証コマンド一式:
   ```powershell
   portable\python\python.exe test_logic.py
   portable\python\python.exe test_autotrack.py
   portable\python\python.exe test_pipeline.py
   portable\python\python.exe test_detect_view.py
   portable\python\python.exe test_make_report.py
   portable\python\python.exe web_gui.py --check
   ```
6. worktree並行開発の教訓: 複数エージェントが `run_pipeline.py` を触ると統合が重い。
   マージベースが古い場合は **ブランチのマージではなく作業コミット単体の cherry-pick**
   が競合を最小化する（第2波Dで実績）。統合後は必ず全テスト＋ID1受け入れ再実行

### (2) ID5 574.3s の追跡失敗 — **回収**

原因は**トラックの乗り移り**だった。フレーム5674〜5675 で路肩の物体（X -6.4〜-4.8、

段階3のオフセットは GoPro の GPMF 時刻と PCAP の記録時刻の引き算なので、**LiDAR 収録PCの
時計ずれを原理的に見られない**（260701 では全5セッションで +4.2〜5.2 秒ずれていた）。
段階3.5 は点群から作った自車速度と GPS 速度の相互相関でオフセットを独立に測れるのに、
その値を使うかどうかが `--auto-offset` という**付け忘れ得るフラグ**に委ねられていた。
付け忘れると警告は出るが処理は続き、全イベントの割り当てが数秒ずれたまま最終Excelまで
通ってしまう。

### 直し方

`--auto-offset` を既定で有効にし、無効化する `--no-auto-offset` を足した。判定の中身
（信頼できる推定か・差が3秒超か）は変えていない。

| 状況 | 変更前 | 変更後 |
|---|---|---|
| 差 > 3.0秒・推定が信頼できる | 警告＋人手項目（`--auto-offset` 指定時のみ差し替え） | **差し替えて続行** |
| 推定が信頼できない | 何もしない | 変更なし |
| 差 ≤ 3.0秒 | 記録のみ／警告 | 変更なし |
| `--offset` で手動指定 | 検証しない | 変更なし |

`--auto-offset` は以前のコマンドがそのまま動くよう受け付ける（既定と同じ動作）。
差し替えたときの `sync.json` は従来どおり `source="sync_check"`、段階3の値は
`gpmf_offset` に残る。

テストは `test_pipeline.py` に「既定で差し替える」「`--no-auto-offset` なら保つ」の2件
（差し替え後の `sync.json` と `info["時刻オフセット(秒)"]` まで確認）。48件が成功。

### 申し送り

- `gpmf_sync.compute_gps_offset` 自体は直していない（GPMF からPCの時計ずれは見えない
  ので、原理的に直せない）。段階3.5 を省く `--skip-sync-check` と併用すると、ずれたままの
  オフセットで処理される点は変わらない。**`--skip-sync-check` は時間が惜しいときだけ**。

## 16. 第5波Q: 同時刻に別車線を通る車のグループ化 — **完了**

§14 の申し送り「608.6s のように同一車線の車を追跡側が候補に挙げられていないケース」を
調べたところ、**追跡は成功していて、割り当て前のグループ化が原因**だった。

### 原因

`lidar_autotrack.py --list-tracks` で ID1 の該当区間（フレーム5380-5620）を見ると、
正解の車は `track 211 / f5503x+1.4`（13点・X中央 +1.42・LC目安 0.869 ≒ 正解 1.02m・
score 1.000）として**正しく追跡できていた**。

問題は `run_pipeline.group_vehicles()` で、通過時刻が `VEHICLE_MERGE_GAP`（1.0秒）
以内の候補を無条件に同じ車とみなしていたこと。この区間では

    f5500x+3.0 通過 553.23s / f5502x+3.4 553.43s / f5503x+1.4 553.53s / f5511x+4.2 554.33s

の4トラック（横位置 +1.4〜+4.2m）が**1台に束ねられていた**。さらに判定が「直前の1件
との差」だったため 0.1〜0.8秒ずつ数珠つなぎになり、合計1.1秒（`merge_gap` 超）へ広がる。
束ねたグループは1つのイベントにしか割り当てられず、残りは `unassigned_vehicles` の
`used` 判定で L### としても起票されないため、**同一車線の車がどこにも出てこなかった**。

### 直し方

`VEHICLE_MERGE_LATERAL = 1.5`（m）を新設し、グループ化の条件を「通過時刻が1秒以内
**かつ** 横位置 `median_x` の差が1.5m以内」にした。あわせて比較相手を直前の1件から
**グループの先頭**へ変え、グループの広がりが必ず `merge_gap` 以内になるようにした。

値の根拠: 同じ車が別の追跡窓でぶれる幅（`TRACK_KEY_LATERAL_TOLERANCE` = 1.0m）より
広く、同一車線と隣車線の間隔（ID1 608.6s の実測で +1.4 と +3.0 の 1.6m）より狭い。
`median_x` を持たない候補は従来どおり時刻だけで判定する。

### 効果（260701 の全5ID・正解46件との突き合わせ）

| | 一致 | 正解に無い採用 | 取りこぼし | 採用 |
|---|---|---|---|---|
| 修正前 | 44 | 9 | 2 | 53 |
| 修正後 | **45** | 11 | **1** | 56 |

- **ID1 は 11/12 → 12/12（誤り0）**。608.6s の車が候補 029 へ割り当たるようになった
- ID3 は一致13のまま採用が18→20。増えた2件（021 LC 1.01m・023 LC 2.04m）は正解に
  無い行で、既存の「正解に無い採用」と同じ確認待ちの山に入る
- 残る取りこぼし1件（ID3 GX020735 139.64s）は動画検出の取りこぼしで、`L008`（未確認）
  として起票済み

### 調べたが採用しなかった案

`lc_estimate == 0.0` の候補（クラスタが搭乗者と繋がって最近接が0になったもの）を
足切りする案を検討したが、**割り当て178件のうち19件がこれに該当し、その中には正解と
一致した行（ID1 006・007、ID2 016・018、ID4 003 など）が多数含まれる**ので採用しない。
追跡時のLCはあくまで目安で、実測は段階5の edit CSV で取り直している。
